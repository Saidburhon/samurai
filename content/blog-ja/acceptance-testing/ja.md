納品されたシステムを触ってみたら、思っていたものと違う。不具合を伝えても、直るたびに別の箇所がおかしくなり、検収がいつまでも終わらない。システム開発を外注した会社、とくに海外のチームに頼んだ会社から、よく聞く話です。

原因を開発会社の技術力に求めたくなりますが、実際には、発注側が「どうなれば合格か」を決めないまま納品を迎えている例も少なくありません。この記事では、検収を任された担当者の方に向けて、受け入れ基準の書き方から、テスト環境、日本向けシステムならではの確認項目、不具合の伝え方、検収後の扱いまでを順に説明します。

## 受け入れテストは発注側の仕事

開発会社は納品の前に、単体テスト、結合テスト、システムテストを行います。これらは「仕様書どおりに作れているか」を確かめるテストです。

受け入れテスト（UAT：User Acceptance Testing）は目的が違います。「自社の業務で実際に使えるか」を、発注側が自分たちの手で確かめるものです。仕様書の読み方が食い違っていれば、開発会社のテストにすべて合格していても、業務では使えないということが起こります。

業務の実態をいちばんよく知っているのは発注側です。受け入れテストを開発会社に任せきりにすると、食い違いが見つかるのは検収の段階、つまり直すのにいちばん手間がかかる時期になります。受け入れ基準を書き、確かめるのは発注側の仕事だと最初から決めておくほうが、結果として検収は早く終わります。

## 受け入れ基準は開発が始まる前に書く

受け入れ基準とは、機能ごとに「どうなれば合格か」を文章にしたものです。納品されてから考えるのでは遅く、開発が始まる前、遅くとも各機能の開発に入る前に、開発会社と合意しておきます。

書くときは、人によって受け取り方が変わる言葉を、操作の手順や時間の目安に置き換えます。

- 「使いやすい」→「初めて使う営業担当者が、マニュアルを見ずに顧客の新規登録を3分以内に終えられる」
- 「速い」→「顧客データが10万件ある状態で、氏名で検索した結果が3秒以内に表示される」
- 「正しく計算される」→「税込金額は1円未満を切り捨て、画面・見積書・請求書のすべてで同じ金額になる」

前提・操作・期待する結果の3つに分けると書きやすくなります。「管理者でログインした状態で、退会済みの顧客を検索すると、一覧に表示されない」といった形です。数字は自社の業務に合わせて決めてください。大事なのは、合格か不合格かを誰が見ても同じように判断できることです。

仕様が変わったときは、受け入れ基準も同じ日に直します。基準と仕様がずれたままだと、検収のときにどちらが正しいかで揉めることになります。

## テスト環境とテストデータを用意する

受け入れテストは、本番に近い構成の検証環境で行います。OSやデータベースのバージョン、外部サービスとの連携、メール送信の設定が本番と違うと、検証環境では動いたのに本番では動かない、ということが起きます。検証環境から実在の顧客にメールが届いてしまう事故もあるため、送信先の制限も確かめておきましょう。

テストの期間中に、検証環境をいつ更新するかも決めておきます。確認の途中で中身が入れ替わると、どの版で何を確かめたのかが分からなくなります。

テストデータには、個人情報を含まないものを使います。本番データをそのまま開発会社に渡すのは避けてください。海外の会社に個人データを渡す場合は、個人情報保護法の「外国にある第三者への提供」に関する定めも関わってきます。本番に近いデータが必要なときは、氏名や連絡先を架空のものに置き換えて用意します。

データの量も大切です。10件では快適に動いた画面が、数万件では使い物にならないことがあります。業務の実態に近い件数や、月末に処理が集中する状況を再現できるデータがあれば、性能の問題を早く見つけられます。

## 日本向けシステムで見落とされやすい確認項目

海外のチームは、日本の文字や暦、商習慣に関わる点に気づきにくいものです。技術力の問題ではなく、日常で触れる機会が少ないからです。次の項目は、受け入れ基準とテストシナリオに最初から入れておくことをおすすめします。

| 項目 | 確認すること |
|---|---|
| 全角と半角 | 全角の数字やハイフン、全角スペースが入力されても正しく扱えるか。半角カナをどう扱うか |
| 長い氏名や住所 | 建物名や部屋番号まで入る長さがあるか。画面や帳票で切れたり崩れたりしないか |
| 外字や旧字体 | 「髙」「﨑」「𠮷」などが、入力・保存・表示・CSV出力のすべてで文字化けしないか |
| 和暦 | 和暦での表示や入力が必要か。平成から令和に変わった日をまたいで正しく変換されるか |
| 日本の祝日 | 営業日の計算に祝日や振替休日が入っているか。祝日が変わったときにどう更新するか |
| タイムゾーン | サーバーがUTCで動いていても、日本時間の日付で記録・集計されるか |
| メール文面 | 敬語や宛名の「様」、姓と名の順序、署名が日本の取引先に送って自然か |
| 帳票の印刷 | A4で印刷したときの余白や改ページ、PDFの日本語フォント、金額の表記 |
| CSV | Excelで開いたときに文字化けしないか。取引先が指定する文字コードで出力できるか |

タイムゾーンは特に見落とされがちです。日本時間の午前0時から8時59分までは、UTCではまだ前日です。サーバーの時刻をそのまま使うと、早朝の注文が前日の売上として集計されてしまいます。チームがタシケント（UTC+5）にいる場合、日本の午前0時は現地の前日20時にあたるため、チームの手元のテストでは気づきにくい点です。日付の境目をまたぐテストケースを、意識して入れておきましょう。

## 誰が、何を、いつまでに確認するか

テストシナリオは、画面ごとではなく業務の流れに沿って作ります。たとえば「見積もりを作る、承認する、受注に切り替える、請求書を出す」という一連の操作を、営業担当、承認者、経理といった実際の役割ごとに通して確かめます。月末の締めや年度の切り替えなど、時期によって変わる処理も入れておきます。

シナリオごとに、確認する人と期限を決めます。ここでつまずきやすいのが、業務担当者の時間です。通常業務の合間に見てもらうつもりでいると、ほとんど進みません。受け入れテストの期間は、上長と相談して担当者の時間をあらかじめ確保しておきましょう。結果は、シナリオごとに合否、確認した日、確認した人を一覧に記録します。この一覧が、そのまま検収の判断材料になります。

開発チームが日本より4時間遅い時間帯にいる場合は、時差を活かした回し方もできます。

1. 日本の午前（チームの勤務開始前）に、発注側がテストを行う
2. 日本の13時〜18時（タシケントの9時〜14時）の重なる時間に、見つかった不具合を共有し、不明点を話し合う
3. 日本の夕方以降も、チームは現地の勤務時間内で修正を進める
4. 翌朝、日本側で修正を確認する

## 不具合は再現できる形で伝える

「〇〇の画面が動かない」とだけ送ると、開発側は状況を聞き返すしかありません。時差のある相手だと、そのやり取りだけで1日が過ぎてしまいます。不具合を伝えるときは、次の項目をそろえます。

- 操作の手順（どの画面で、何を入力し、どのボタンを押したか）
- 期待した結果
- 実際の結果（エラーメッセージがあれば、その文言）
- 画面のスクリーンショットや操作の動画
- 端末、OS、ブラウザとそのバージョン
- 重要度（業務が止まる、回避策がある、表示だけの問題、など）

あわせて、仕様変更の要望と不具合を分けて扱います。受け入れ基準や仕様書に書かれたとおりに動いていないなら不具合、書かれていないことを新たに求めるなら変更の要望です。変更の要望は、期日と費用への影響を確かめたうえで、対応するかどうかを決めます。どちらとも言えないものは双方で話し合い、結論を記録に残します。ここを混ぜてしまうと、検収はいつまでも終わりません。

## 検収と、その後の扱い

検収は、受け入れテストの結果をもとに「契約どおりに納品された」と認める手続きです。支払いや責任の範囲にも関わるため、次の点は契約の段階で確かめておきます。

- **検収の期限**：納品から何日以内に合否を出すか。期限内に連絡がなければ合格とみなす条項があるか
- **合否を判断する人**：現場の担当者か、決裁権を持つ人か
- **条件付きの合格**：軽い不具合が残っている場合に、修正の期限を決めて合格とする扱いを認めるか
- **契約不適合責任**：検収後に不具合が見つかったとき、どの期間、どの範囲で、どう対応してもらえるか。2020年4月に施行された改正民法で、それまでの瑕疵担保責任から考え方が変わっています
- **保守契約への移り方**：契約不適合責任として直すものと、保守として扱うものの境目。問い合わせの窓口と対応時間

具体的な期間や条件は、案件ごとに契約で決めるものです。請負契約か、ラボ型に多い準委任契約かによっても責任の考え方が変わるため、必要に応じて社内の法務担当者にも相談してください。

## 品質は最後のテストだけでは作れない

ここまで検収の進め方を書いてきましたが、最後にまとめてテストするだけで品質を確保するのは難しいのが実情です。遅い段階で見つかった問題ほど、直すのに時間も費用もかかります。

そこで、次のような進め方を最初に決めておきます。

- 週次のデモで、作りかけの画面を早いうちから実際に触る
- 機能を小さく区切り、区切りごとに受け入れテストを行う
- 開発側のテストを通っていないものは、検証環境に出さない

3つ目は当たり前に見えますが、納期が迫ると「とりあえず見てください」と、確認の済んでいないものが出てきがちです。最初に決めておけば、発注側の確認の時間を無駄にせずに済みます。

Qilichも、受け入れ基準を開発の前に発注側と一緒に決め、週次のデモで動くものを見ていただきながら、区切りごとに受け入れを進めることを基本にしています。
